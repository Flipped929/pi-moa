# pi-moa 实测报告（Evaluation Notes）

> 数据来源：pi-moa 在一个真实企业级 Java 项目（RuoYi 底座，20+ 业务模块）上的三次实战任务。
> 所有内容已脱敏：隐去项目名称、业务细节与路径，仅保留方法、数据与结论。
> 这些数据是**调度规则当前形态**的依据，也是希望社区帮忙继续打磨的部分（见文末开放问题）。

## 任务① 全文档审计（高重叠阅读类）—— MoA 输了，学到最多

**任务**：核对一份 51KB 系统设计文档全部"已完成"标注的代码真实性。

| | MoA 三路（analyst×2 + critic @ flash） | 影子基线（单强模型 K3） |
|---|---|---|
| 总 token | **304,607** | **116,625** |
| 强模型额度消耗 | 仅聚合（~数千） | 全部 116,625 |
| 现金成本 | flash 毛级 | 0（订阅内） |
| 质量 | 发现 2 项安全失真 + 8 处文档矛盾 | 发现更全（多 3 项安全隐患）；还纠正了 MoA analyst 的 1 处误判 |

**失败根因**：
1. 高重叠任务：三路子模型各自把同一文档重读一遍（"重叠税"，token 2.6x）
2. flash analyst 把 git 提交说明当实证（"验证通过"字样），漏验种子数据本体

**产出的规则**：
- 调度矩阵新增"重叠度评估"前置：高重叠阅读类 → 0-1 子模型，或"一读多评"（1 analyst 通读产摘要黑板，其余角色只抽查不重读）
- 实证纪律铁律：提交说明/注释/"验证通过"字样一律不算实证

## 任务② 机械安全配置修改（低风险机械类）—— 打平，critic 冗余

**任务**：6 个文件中的明文密钥改为环境变量注入。

| | MoA（executor+critic） | 影子（单 K3，git worktree 隔离独立做） |
|---|---|---|
| 总 token | 101,130（executor 53,942 + critic 47,188） | 40,577 |
| 时间 | 2.6 min | 1.1 min |
| 质量 | **两版 diff 逐字节一致**（仅 1 行注释措辞差异） | 同 |

**结论**：低风险机械修改，critic 全程审查性价比低 → 规则修订：此类任务 1 executor + captain 抽查即可，critic 改抽样触发。

## 任务③ 双模块并行开发（scope 不相交编码类）—— MoA 首胜，价值正名

**任务**：两个互不相交的新模块（后端 Controller/Domain/Mapper/SQL + 前端页面）并行开发。

| 单元 | tokens | 关键事件 |
|---|---|---|
| executor-A + executor-B（并行） | 149,585 | 零碰撞交付 11 个文件 |
| critic | 84,754 | **抓出致命逻辑 bug**：匹配算法自匹配导致检测结果恒为"通过"（上线即废品）；同时产出 1 个误判 |
| executor-fix | 81,943 | 按审查清单修复，全项目编译通过 |
| 合计 | 316,282（flash，现金毛级） | 同工作量单 K3 需数倍订阅额度且串行更慢 |

**结论**：
- 验证链 `executor → critic → captain 抽查` 两层都工作：critic 抓 executor 的致命 bug，captain 抽查驳回 critic 的误判
- 并行零碰撞靠设计：共享文件禁碰 + 各写独立 SQL fragment + scope 互不相交
- **MoA 的甜区 = 高风险 / 强异构 / scope 不相交的大并行**

## 三次任务共同沉淀的调度规则 v1（现行）

| 任务类型 | 子模型数量 | 模式 |
|---|---|---|
| 高重叠阅读类（全文档审计/全景勘察） | 0-1 | 单模型或"一读多评" |
| 编码类（scope 不相交） | 2-3 | executor 并行 + critic 审 diff |
| 评审类（输入材料小） | 3 满编 | analyst/critic/devil 对抗多轮 |
| 调研类 | 2-3 | analyst 分角度 |
| 写作类 | 2 | executor 起草 + critic 挑刺 |
| 低风险机械修改类 | 1 | executor + captain 抽查（critic 抽样触发） |
| 小任务（<10 分钟） | 0 | captain 直接干 |

## 🔬 开放问题（Help Wanted）

以下问题我们没有足够数据回答，**欢迎社区用实测数据/提案参与**（见 README「参与共建」）：

1. **子模型数量的最优曲线**：3 是拍脑袋上限。是否存在随任务规模变化的函数？什么指标决定该加一路还是减一路？
2. **重叠度的量化**：目前靠 captain 主观评估。能否用文件集交集率/上下文相似度自动计算，前置到派活之前？
3. **任务分配的切片算法**：按文件？按模块？按符号依赖图？哪种切片让 executor 返工率最低？
4. **抽查率的动态调整**：角色可信度用误判率一阶近似是否合理？应该有遗忘因子/贝叶斯更新吗？
5. **影子基线的自动化**：多大抽样比例能在可接受成本内保持基线校准？
6. **handoff 质量度量**：dead_ends 的信息量如何量化，进而驱动"何时该 handoff 而不是硬撑"？

> 如果你有想法：开一个 issue（`[feat]` 模板），或用 `docs/playbooks.md` 的方法自定义模式做实验，把对比数据 PR 到本文件。
